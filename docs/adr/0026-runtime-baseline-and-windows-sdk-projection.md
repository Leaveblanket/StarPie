# 运行时基线与 Windows SDK 投影版本政策：.NET 段跟随 LTS 升级、windows 段独立钉住 19041

> Status: Active
>
> 现状正典：各 `.csproj` 的 `TargetFramework` 与根 `global.json`；程序集/技术栈表述见 `docs/architecture.md` §3。

## 动机

1. **TFM 两段语义被混为一谈**：`net10.0-windows10.0.19041.0` 的 `.NET` 段决定运行时、BCL 与语言面，`windows` 段决定 WinRT 投影面。两段一起动，运行时替换与 API 投影替换就无法在验证中归因（投影是 ADR-0013 选中 `19041` 的直接原因：`UISettings.ColorValuesChanged`）。
2. **运行时基线会周期性到期**：.NET 版本有支持期终点，仓库此前没有任何 SDK 固定点，构建与发布实际使用的 SDK 由环境决定，同一提交在不同机器上可能落到不同工具链。
3. **自包含发布改变了兼容性问题的性质**：产品以自包含单文件分发，用户机器上的运行时安装与本应用无关，因此“保留旧 TFM 以兼容用户环境”这一常见理由在此不成立。

## Considered Options

- **只升 `.NET` 段、`windows` 段钉住 `19041`** → 采纳：一次迁移只有一个变量，投影面行为可沿用既有验证结论。
- **同时抬 `windows` 段（如 `10.0.26100.0`）**：新投影 API 与 CsWinRT 代际一并变动，与运行时替换混成不可归因的变更面 → 否；有真实新投影需求时独立成批、独立验证。
- **多目标 `net8.0;net10.0`**：终端应用、无外部消费者，多目标换来的是 xUnit 与 e2e 验证面翻倍，没有真实兼容收益 → 否。
- **不引入 `global.json`**：SDK 漂移保留，CI（`setup-dotnet`）与本地/e2e 各自为政 → 否。

## Decision

1. **运行时基线跟随 .NET LTS**：全部工程 TFM 的 `.NET` 段在支持期结束前升级到受支持版本；不保留上一代 TFM，不写按 TFM 分叉的条件编译。
2. **`windows` 段独立演进**：投影版本维持 ADR-0013 选定的 `10.0.19041.0`，只随真实 API 需求变更，且该变更必须与运行时升级分开。
3. **SDK 基线入库**：`global.json` 固定 SDK 版本与 `rollForward` 策略，本地构建、CI 与 e2e 共用同一基线。
4. **运行时相关包同版本族**：`Microsoft.Extensions.*` 等与运行时同步演进的包跟随基线版本族，不长期跨代混用；与运行时解耦的测试栈（xUnit 等）独立演进，不随本政策捆绑。
5. **迁移零行为变化**：基线升级批次不夹带 UI/主题/文案/交互改动，验证面为 build + 全量 xUnit + 全量 pywinauto e2e + 自包含单文件产物。

## Consequences

- 后续每次 LTS 升级的改动面被限定为：TFM 的 `.NET` 段、`global.json`、运行时相关包版本；`windows` 段与投影相关代码不动。
- 抬 `windows` 段（例如为了新 WinRT 投影能力）总是独立议题，需要独立评估与独立验证，不能搭运行时升级的车。
- 因投影包按旧段解析，投影相关行为在运行时换代时保持连续；怀疑投影行为回归时，问题域被限定在运行时替换本身。
