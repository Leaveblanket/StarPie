# UI 插件不承诺 ALC 真卸载：卸载语义降级为「托管清理 + 可验证 + 泄漏隔离 + 重启生效」

> Status: Active（决策 1 对 headless 的承诺边界被 [ADR-0035](0035-wpf-host-plugin-assembly-reclaim-downgrade.md) 修订：WPF 宿主里 headless 插件同样不承诺 ALC 回收）
>
> 本文修订 [ADR-0028](0028-plugin-ui-hosting-and-host-managed-lifecycle.md) 决策 4（卸载管线的最终验证）与决策 6（承诺分级）；其余条款（宿主托管资产、资产登记表、受支持特性白名单、信任前置）继续有效。目标态规范见 `docs/architecture/plugins.md`。

## 动机

1. **UI 插件程序集在进程内不可回收**：只要插件程序集里的类型或 BAML 资源被 WPF 触碰过——进视觉树、被模板套用、被资源查找、被依赖属性或类型描述符缓存——该程序集就再也不回收。以一次性打样（`prototype/p0-wpf-alc` 分支，13 项探针 + 逐变量归因）验证：把**纯 POCO** 放进宿主容器就足以钉住程序集；用私有反射清空 5 处可定位的 WPF/BCL 全局缓存（`SystemResources._dictionaries`、`SafeSecurityHelper._assemblies`、`DependencyObjectType.DTypeFromCLRType`、`TypeDescriptor` 两处）后扫描命中归零，ALC 与程序集**依旧存活**。追加取证（SOS + 托管堆转储 + 穷举清缓存实验，见 `prototype/p0-wpf-alc` 分支 `p0-forensics.md`）把该根定位为**多层 WPF 内部缓存与运行时内部句柄的组合**：共享 BAML 类型表、资源管理器注册表、绑定访问器表、全局事件 DTypeMap、打包层预载缓存逐层露出；清掉全部可定位层后，残余仍是托管代码无法释放的插件 `RuntimeType` 句柄。
2. **与之相对，不触 WPF 的路径可回收**：仅装载程序集、以及只实例化插件 POCO 而不交给 WPF 的场景都能回收。根因因此不在插件是否自觉清理，而在 WPF 的全局缓存；插件的清理行为再规范也无法绕过。
3. **不显式降级就会建设不可实现的验收**：ADR-0028 决策 4 把「`ALC.Unload()` 后 WeakReference 判定」写成了卸载管线的收尾断言，决策 6 又承诺 headless 与 UI 分级。若不在规范层把 UI 插件的承诺改成可验证的那部分，P3 会按「UI 插件可热卸载/热更新」施工。

## Considered Options

- **维持 UI 插件真卸载承诺，靠清 WPF 全局缓存实现** → 否。需要长期依赖未公开的私有静态缓存，且实测即使清空全部可定位缓存仍不可回收，承诺不可兑现。
- **放弃进程内 UI 插件，退回纯 headless 生态** → 否。卸载承诺可保住，但插件生态退化为无界面，与 ADR-0028 修订 ADR-0027 的动因冲突。
- **保留进程内 UI 插件，把承诺降级为可验证的那部分** → 采纳。

## Decision

1. **承诺分级重写**：headless 插件承诺 ALC 真卸载；**UI 插件（任何触及 WPF 类型或 BAML 的插件）不承诺程序集回收**，只承诺「资产登记表清零 + 插件对象可回收 + 全局根扫描无残留 + 泄漏隔离」。
2. **UI 插件的更新语义 = 隔离旧版本 + 下次启动装载新版本**：不做运行期热重载，也不做无约束即时重载；停用、重载、更新三种动作在管理面必须可区分。
3. **验收口径随之调整**：UI 插件只对「资产清零 / 插件对象与插件委托 WeakReference 全死 / 全局根扫描无插件残留」判失败；`ALC.Unload()` 仍执行，但「ALC 与程序集未回收」只作为诊断上报，不判失败、不置 `Quarantined`。`Quarantined` 只留给资产未清零、全局根有残留、调用失败这三类真问题。
4. **受支持特性白名单不变**，逐项仍以「资产可清零」为判据；其中宿主中介动画必须以 `Storyboard.Remove(元素)` 摘除，只 `Stop()` 会残留。

## Consequences

- 泄漏验证器的判定分成两层：可判定项（资产、插件对象、全局根）计失败，诊断项（ALC/程序集存活）只上报；`ALC.Unload()` 之后的二次判定保留为诊断，不得据此谎报成功。
- 插件管理面与状态机的语义要相应区分：UI 插件的「重载/更新」不再等于「立即换新版本」，需要向用户显式表达「下次启动生效」。
- UI 插件的资源占用在多次更新后可能因无法回收而累积（旧版本程序集留在进程内），「彻底移除」需配合重启才真正释放内存。
- 若将来 .NET/WPF 提供受支持的缓存失效或 ALC 卸载路径，可另立 ADR 恢复真卸载承诺。该路径已被穷举清缓存实验证否（受支持手段内清理不收敛），不再作为待办追踪。
