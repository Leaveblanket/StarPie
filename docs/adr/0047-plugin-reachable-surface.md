# 插件可达面：程序集导出面不等于插件可用面

> Status: Active

## 动机

1. **一处真实的混淆**：`IThemeService` 驻 `StarPie.Sdk.Wpf`（插件引用的程序集），也在导出面白名单里，
   于是被登记为「插件可见面」，并据此提出「契约偏宽、应削窄」。但插件的全部宿主可达面其实只有两个
   上下文的成员：`IPluginContext`（插件 id、日志、事件、能力注册）与 `IPluginUiContext`（一串注册
   漏斗）——两者都没有任何取服务的方法，宿主也不给插件组合根或服务定位器。该类型的**实例**对插件
   不可达：不存在注入边。
2. **据此削窄的代价被低估**：删成员属破坏性变更，要递增 ABI 主版本；而兼容判定要求同主版本，
   一次会拒掉全部在网插件（随包清单也要改），收益只是白名单里少三个成员。
3. **插件侧的既定形态本就是探针**：深浅色读数不需要服务实例——轮盘侧原经该契约的允许边已清零，
   改经无状态 `Func<bool>` 探针，这条路已经走通。

## Considered Options

- **削窄为「只留窗口效果面与当前有效主题」** → 否。这不是插件侧的实际需要：深浅色读数由无状态探针
  满足（既定形态），而窗口效果面（给插件托管的窗口套 DWM 标题栏）目前没有任何插件消费方；
  代价仍是删除成员，收益只是少几个成员。
- **删成员 + 主版本递增** → 否。代价是拒绝全部在网插件，与收益不成比例；应在真有插件消费主题能力时
  一次性付清，而不是为了白名单整洁提前付。
- **把该类型移回宿主集**（它确实没有插件消费方，是宿主内部接缝借住在 SDK 集）→ 否（本次）。
  同样要付导出面移除的代价，还要动程序集地图与边界断言，而插件侧的实际处境（不可达）并不因此改变。
- **不引入可达边，改为把「可达面」定义下来并机械守护** → 采纳。类型与导出面保持原样，改动落在判定上：
  将来谁往插件面加服务成员，断言会先拦下他。

## Decision

1. **插件可达面 = 从 `IPluginContext` 与 `IPluginUiContext` 的成员签名出发、可传递到达的宿主类型集合**。
   程序集导出面是**引用面**（哪些类型可被引用），可达面是**能力面**（插件实际能拿到什么服务）——
   两者不是一回事；涉及「插件能不能做什么」的规范与评审一律以可达面为准。
2. **主题不进可达面**：插件侧的深浅色需求由宿主注入的无状态探针满足（既定形态），`IThemeService`
   保留在 `StarPie.Sdk.Wpf` 作为宿主与对话框侧的接缝，**不**为插件引入注入边，也**不**删成员。
3. **可达面由机械断言守护**：一条从两个上下文做成员签名传递闭包的测试，断言主题服务不在闭包内。
   它拦的是「新增或修改的成员签名触及本仓四集类型」这一类改动——那正是往插件面加服务会走的路；
   签名只触及平台类型（如 `IServiceProvider`）的成员不在此列，那也是插件面约束本身禁止的形态。

## Consequences

- 该契约的成员宽度对插件不再构成风险：插件拿不到实例，写入面也就无从绕过宿主编排。
  主题在插件侧走无状态探针，是现行规范而非待办。
- 将来若要给插件真正的主题能力（例如宿主托管渲染插件窗口的标题栏），做法是新增窄能力与其标识，
  仍不必动既有契约——本决策把「何时该付主版本代价」推迟到有真实消费方的那一刻。
- 闭包只沿本仓四集的类型走、不追平台类型：这是「插件可达的**宿主**面」的口径，WPF 与 BCL 类型不在此列。
  今天两个上下文的闭包与一层签名面重合（尚无经成员再走一跳的本仓边），传递这一半是给后续成员准备的。
