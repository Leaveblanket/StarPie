# 提权实例接管非提权实例：即时提权复用路线 B 的任务，让位严格单向并经命名内核对象握手

> Status: Active
>
> 本文**修订** [ADR-0042](0042-privilege-routes-two-only.md) **决策 2 的边界**（收窄为"不提供 `runas`
> 提权重启"）与其 Consequences 中"运行期改变权限级别的唯一方式是改开关并重启"、
> ""已有实例在跑时右键以管理员身份运行"不受支持"两条表述。ADR-0042 决策 1（两条路线互斥）继续承载。
> 契约正典：`docs/architecture/shell.md`（自启面与高级设置面）、`docs/architecture/host.md`（单实例闸门）；
> 术语见 `CONTEXT.md`（提权 / 提权自启 / 立即提权 / 接管与让位）。

## 动机

1. **权限路线收敛顺手丢掉了"立即"这个维度**。提权的唯一入口变成提权自启，而它的落位形态是
   `onlogon`——打开开关对当前正在运行的实例毫无影响，必须注销或重启才生效。用户照着开关说明
   （"可在任务管理器等高权限窗口中正常唤起手势"）打开它，然后发现没有反应，也没有任何东西告诉他为什么。
2. **用户手边那条路径被静默吞掉**。右键「以管理员身份运行」会弹一次 UAC、把既有设置台置前、
   新进程无声退出——单实例闸门把"权限更高的同一个程序"当成了"重复启动"。用户白付一次 UAC，
   一无所获，也没有一句解释。
3. **需要的机制其实已经在手**。`schtasks /run` 让**非提权**进程触发一个 `/rl highest` 任务，
   由任务计划程序服务拉起一个 High 完整性级别、同一交互会话的实例，**全程无 UAC**——这正是路线 B
   已经拥有的那颗任务，只是触发时机从"登录时"变成"登录时或用户要求时"。它不提供路线 A/B 之外的
   任何能力，因而**不是第三条权限路线**。
4. **接管必须严格单向**。接管的目的只有"提升权限"一种。非提权新实例遇到提权既有实例时若也让它让位，
   一次误双击就能把用户的提权状态撤销掉；同一提权级别相遇则接管不产生任何收益，却要付一次进程交接的代价。
5. **握手不能借道窗口消息**。UIPI 按完整性级别拦消息，而"提权实例能否向非提权实例投递注册消息"
   是未实测的推断；命名内核对象同用户跨完整性级别可开，换信道即可消除这层不确定性。
6. **就绪不能看触发命令的退出码**。实测 `schtasks /run` 返回成功只表示"任务被受理"：动作为空的
   任务被触发时同样返回成功，而进程根本没有启动。就绪判据只能来自"既有实例确实放手了"。
7. **失败的结论必须有人说得出口**。提权没成时新实例即将退出，无处呈现；而它留下的那个
   "什么都没发生"正是用户最需要解释的场景。

## Considered Options

- **恢复 `runas` 提权重启（每次 UAC）** → 否。它把提权重新变成逐次成本，也把混合权限态重新变成常态；
  即时提权不需要付这笔成本——建任务那一次 UAC 用户已经付过了。
- **只把"需重启生效"写进开关说明，不恢复运行期提权** → 否。写清代价不等于给出能力，而能力已经在手
  （动机 3）。用户要的是"现在就能用"。
- **为应用内入口开一条专用通道（另建任务、另走握手）** → 否。同一件事两套机制必然漂移。接管的发生点
  收敛在单实例闸门一处，应用内触发、右键 `runas`、`schtasks /run` 三条来路共用同一条规则。
- **对称接管（谁权限高谁活，两个方向都让位）** → 否，见动机 4。
- **用窗口消息做让位握手** → 否，见动机 5。
- **把触发命令的退出码当作"提权实例已就绪"** → 否，见动机 6；等待"单实例互斥体可取得"才是判据。
- **把即时提权做成第三种形态（临时建任务、用完删任务）** → 否。入口只在任务已存在时可用，
  没有"临时建任务"的语义，也就没有新的生命周期要管。
- **让位时旧实例只在内存里放手（不落盘、不释壳）** → 否。旧实例必须走既有退出编排
  （落盘 → 释托盘 → 关闭），否则用户会丢掉未落盘的编辑，托盘图标与全局鼠标钩子也会出现两份。
- **即时触发 + 严格单向接管 + 命名内核对象握手（采纳）**。

## Decision

1. **即时提权是路线 B 的即时触发形态**：应用内「立即以管理员身份重启」（托盘菜单项与设置页按钮
   是同一件事）触发提权自启那颗计划任务（`schtasks /run`），由服务拉起提权实例；触发本身不需要提权，
   全程不弹 UAC。提权仍只由路线 B 获得——不恢复 `runas` 提权重启、不写 `app.manifest`、不提 UIAccess。
2. **入口只在任务已存在且当前非提权时可用**：已是管理员权限运行时不出现（提权入口只在非提权态出现）；
   提权自启关闭、任务不存在时不可点并说明原因（需先开启该开关）。不做"临时提权、用完删任务"的形态。
3. **接管判定严格单向**：新实例提权 + 既有实例非提权 → 请求让位；提权 + 提权 → 置前退出；
   非提权 + 任意 → 置前退出。接收端同理：只有非提权实例受理让位。
4. **判定只在单实例闸门一处发生**：三条来路共用同一条规则，不给应用内入口开专用通道。接管成功后新实例
   持有互斥体、建托盘与全局钩子；让位的旧实例走既有退出编排，不新增退出路径。
5. **握手信道、就绪判据与失败告知**：握手用命名内核对象而非窗口消息（两个方向、后果不同的信号必须是
   两个独立对象）；就绪只认"单实例互斥体已可取得"，触发命令的退出码不参与判定；提权未成时由既有实例
   经气泡通道说明原因与后续动作。具体命名、dev 实例后缀、时限与降级规则正典见
   [host.md](../architecture/host.md) §单实例闸门。

## Consequences

- **提权不再是纯登录形态**：运行期也能得到提权实例。代价是"提权态"重新成为可能随时出现的中间态，
  但**不随之恢复**那批为混合权限态服务的适配——子进程降权、动作项提权、高权限窗口一次性告知
  都不回归；子进程继承管理员令牌仍是提权形态的既定代价（[ADR-0042](0042-privilege-routes-two-only.md) 决策 4）。
- **旧实例必须先完成落盘与释壳才算让位**，中间有数秒窗口；等不到就让本次提权作废，用户需重试。
  宁可失败，也不把"用了半截的旧实例"与"接管失败的新实例"同时留在用户机器上。
- **握手对象是同一用户下可写的全机命名对象**：同用户的其他进程可以置位它，从而使非提权实例让位。
  信任边界与既有的单实例恢复消息、测试实例退出消息同口径——它们同样只靠"同机同用户"划界。
- **跨 dev/正式形态的接管不成立**：两种形态共用单实例互斥体却不共用握手对象，故提权尝试读不到同形态
  标记时退回置前退出。dev 提权不会接管正式版实例（反之亦然），代价是混合形态下这条路径静默降级。
- **跨完整性级别的接管无法被不提权的自动化环境覆盖**：验收只能靠一次真实提权实例 + 一次真实非提权实例
  （口径与 [ADR-0040](0040-startup-privilege-policy.md) 相同）。"成功路径绝不提示"这类性质因此由结构约束
  （失败信号只在一格置位）加人工验收守，而不是由自动断言守。
- **右键 `runas` 的语义被改写**：已有实例在运行、且它是非提权实例时，右键「以管理员身份运行」不再是
  被拦下并置前既有实例（[ADR-0042](0042-privilege-routes-two-only.md) 的对应推论随之失效），
  而是在旧实例让位后真正生效——用户付的那次 UAC 换来了一个提权实例。
