# 权限路线收敛为两条：普通权限启动与管理员权限静默启动

> Status: Active（决策 2 的边界被 [ADR-0043](0043-elevated-instance-takeover.md) 收窄）

> 立即提权 / 接管与让位）。

## 动机

1. **同一个问题曾有三次作答**：进程权限级别此前有三个来源——asInvoker 双击（普通权限）、
   提权自启计划任务（管理员权限、静默）、运行期点一次提权重启（管理员权限、弹 UAC）。
   三者里前两者的差别是**权限级别**，后两者与前两者的差别只是**到达提权的时机**（不必重启）。
   这个"时机"收益换来的是"提权态"从登录时定死的形态退化为随时可能出现的中间态。
2. **中间态需要一层适配来兜底**，而这一层是纯开销：高权限窗口一次性告知（因为用户可能不知道自己
   没提权）、提权态子进程经 Explorer 中介降权（因为提权进程拉起的程序会继承管理员令牌）、
   动作项上的"以管理员身份启动"（因为降权之后反向能力得单独给）——它们的存在理由都指向
   "用户可能在提权态与未提权态之间来回"，而这件事在只有两条路线时不再发生。
3. **两条路线已覆盖真实需要的全部**：不想提权的人要的是静默常驻与普通权限（否则资源管理器拖拽、
   映射盘可见性与 Chromium 系启动都会出问题）；想在高权限窗口里用手势的人，可选的形态是
   **登录即静默提权**，而这一次选择正是他表达"我愿意承担提权代价"的地方。
4. **入口数量与可解释性成反比**：三个入口使"我现在是什么权限、为什么"需要三套说辞；
   两条路线互斥时，权限级别成为登录形态的直接函数，开关状态即答案。

## Considered Options

- **维持三入口（现状）** → 否。那条额外的运行期提权路径不提供任何前两条没有的能力，
  只提供"更快到达提权"，却让三处适配有存在理由；把它去掉之后，适配层整层消失。
- **只留普通启动 + 运行期提权（去掉提权自启）** → 否。这等于回到 ADR-0040 决策 2 的形态：
  提权必然伴随 UAC，且在拒绝即不提权；"高权限窗口内可用手势"退化为一次性机会而不是稳定承诺。
  提权自启是唯一让该收益成为常驻事实的路线。
- **保留提权自启但注册表 Run 键照写（现状兜底）** → 否。两条自启路径的触发时机相同（都在登录时），
  同时落位会让非提权实例与提权实例抢单实例闸门，谁先抢到谁活；非提权那个赢了就等于提权自启白开，
  而界面读计划任务实况仍会显示"已开启"——功能静默失效且无任何线索。
- **为运行期提权保留 UIAccess（不拿管理员令牌也能跨 UIPI）** → 否，理由与 ADR-0040 相同
  （须签名 + 安全位置安装，机制被文档定位为助残技术专用，非管理员账号仍填不满）。
- **asInvoker 普通启动 + 提权自启静默启动，两者互斥且取消其余入口与适配** → 采纳。

## Decision

1. **进程权限只有两条路线，且互斥**：
   - **路线 A｜普通用户权限启动**：asInvoker 双击启动，或 HKCU Run 键登录自启。
   - **路线 B｜管理员权限静默启动**：Windows 任务计划程序任务，提权由任务计划程序服务在触发时完成，
     不弹 UAC。
   两形态的落位规则（互斥、提权形态下注册表 Run 键缺位）正典见 [shell.md](../architecture/shell.md) 关键流程 3。
2. **提权只能由路线 B 获得，且不提供 `runas` 提权重启**：托盘菜单项、设置页提权按钮与
   `AppHostDelegates` 上的**提权重启**（每次弹 UAC 的那一种）委托一并移除。Sdk 导出面在 1.0 之前可变，
   本次是首个删除性变更。**边界收窄**：路线 B 的**即时触发**形态不在此列——它的触发时机从"登录时"
   扩到"登录时或用户要求时"，复用的仍是路线 B 那颗任务，不提供两条路线之外的任何能力
   （见 [ADR-0043](0043-elevated-instance-takeover.md)）。
3. **不写 `requestedExecutionLevel`**，不提 UIAccess（ADR-0040 决策 1 继续承载）；绿色单文件分发形态不变。
4. **子进程权限不做适配**：动作启动的子进程一律沿用调用方进程的令牌，动作项不提供
   "以管理员身份启动"选项；提权态下由轮盘启动的程序继承管理员令牌。
5. **提权态不做超出披露的处理**：高权限窗口内手势失效不再有一次性告知（该告知的点击动作指向的
   正是被本文移除的提权重启；即时提权回归后该告知仍未恢复，见
   [ADR-0043](0043-elevated-instance-takeover.md)）；插件管理页的提权警示**保留**——它是
   [ADR-0029](0029-plugin-trust-model.md) 要求的"用户可见文案必须写清插件与 StarPie 同权限"的
   披露落点，不是混合权限态的适配。
6. **单实例跨完整性级别握手保留**：路线 B 常驻时用户仍可能双击起第二个实例，它必须被拦下并把
   置前请求交给提权实例（`ChangeWindowMessageFilterEx` 放行本进程自有的注册消息；互斥体打开失败
   按"已有实例"处理）。

## Consequences

- **提权态下子进程继承管理员令牌**：资源管理器往其窗口拖文件失败、映射网络驱动器不可见、
  Chromium 系应用拒绝以管理员启动。这是路线 B 的代价，选择它的用户一并接受；不再有"默认降权"这层缓冲。
- **未提权时在高权限窗口内手势失效，且不再有任何提示**。用户可用的补救是把自己提到路线 B：打开提权自启
  开关（下次登录生效），或直接「立即以管理员身份重启」（当即生效，见
  [ADR-0043](0043-elevated-instance-takeover.md)）；开关说明里写明该收益（可在任务管理器等高权限窗口中
  正常唤起手势）。
- **插件随宿主提权**（ADR-0029 的进程内全信任）依然成立，披露点是提权自启开关的说明与
  插件管理页那行警示；提权态不拒绝加载插件——准入决策已交给用户，不因权限级别被二次否决。
- **提权自启不再有"计划任务被外部删除后的兜底自启"**。开关状态本就读计划任务实况，任务被删除时
  开关会如实显示已关闭，故这一兜底的必要性已由实况回读承担。
- **"改开关并重启"不是改变权限级别的唯一方式**：路线 B 那颗任务也接受按需触发，用户可在运行期得到
  提权实例（见 [ADR-0043](0043-elevated-instance-takeover.md)）；两条路线本身仍互斥，即时提权不是第三条。
- **跨完整性级别的两条行为（托盘窗口的消息放行、互斥体失败分支）仍无自动覆盖**：不提权的
  xUnit/e2e 环境复现不了，验收只能靠一次真实的提权实例 + 非提权双击，口径与 ADR-0040 相同。
- **"已有实例在跑时右键以管理员身份运行"的行为已由 [ADR-0043](0043-elevated-instance-takeover.md) 改写**：
  既有实例为非提权时，这次尝试在旧实例让位后真正生效，不再是被拦下并置前既有实例。
