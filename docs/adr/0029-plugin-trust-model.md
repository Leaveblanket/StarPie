# 插件信任模型：签名 + 审核白名单为准入判据，当前开发者模式放行，进程内全信任显式披露

> Status: Active
>
> 本文收口 [ADR-0027](0027-plugin-architecture-and-host-sdk-ui-split.md)「ALC 不是安全边界」与 [ADR-0028](0028-plugin-ui-hosting-and-host-managed-lifecycle.md) 决策 7「信任前置」留下的未决项：**第三方插件凭什么被允许装载**。规范落点见 `docs/architecture/plugin-contracts.md` §5。

## 动机

1. **加载隔离不是安全边界**：进程内插件（含 UI 插件）与宿主同权限——可读 `config.json`、可装钩子、可使进程崩溃、可绕过任何宿主契约。宿主对"装载后它会不会拖垮进程"没有技术兜底，只剩"装载前信不信它"。
2. **开放生态与准入强度是一对真实矛盾**：准入越强，第三方开发者门槛越高；越弱，用户承担的隐性风险越大。这个取舍必须显式决策，不能靠默认值滑过去。
3. **当前没有真实第三方**：插件作者只有本仓库自己。此时投入证书基建与审核流程收益为零；但若不先定下准入闸门与状态载体，将来开放第三方时会临时发明一套不可回退的机制。

## Considered Options

- **签名 + 人工审核白名单**：可信度最高，需要证书基建、审核流程与撤销机制；对"尚无第三方"的当前是空转 → 采纳为准入判据，待生态开放时启用。
- **允许侧载已签名插件 + 风险披露**：开发者体验最好，但把信任决策整体转嫁给用户，且签名本身只证明"谁写的"、不证明"写着安全" → 不采纳为默认。
- **不可信插件走进程外**：真隔离、可强杀卸载，但 UI/性能/调试/生态成本高，与"进程内真卸载"的决策冲突 → 否，保留为未来后端。
- **开发者模式准入 + 签名白名单判据** → 采纳。

## Decision

1. **准入判据 = 签名 + 审核清单**：第三方插件须签名（Windows Authenticode 或受 pin 的发布者证书）且命中可离线校验的审核清单，未命中即 `Rejected`；**不做默认侧载放行**，也不提供"忽略警告继续"的一次性放行——避免把信任决策默认转嫁给用户。清单格式、验签实现、撤销通道与降级策略的现行落点见 [plugin-contracts.md](../architecture/plugin-contracts.md) §5。
2. **当前准入范围**：只允许第一方随包插件与**开发者模式**插件。开发者模式是显式开关（默认关闭），开启时向用户展示进程内全信任风险披露，逐条列出：可读配置与插件数据、可执行任意代码、可使进程崩溃、卸载可能失败并被隔离。
3. **进程内 = 全信任**：一切插件（第一方 / 第三方 / headless / UI）在进程内与宿主同权限；宿主**不承诺**沙箱、权限限制或资源配额。
4. **进程外后端是未来选项**：需要承载"不可信但仍要用"的插件时另起 ADR，不在本决策的承诺范围内。**复启判据**：出现"须装载未命中审核清单的插件"的真实需求（用户自备包、免审核分发）——判据不成立时维持进程内单后端，不为"理论上更安全"预研。

## Consequences

- 验收门：开发者模式关闭时第三方来源插件必须被拒；开启时必须给出完整风险披露（文案 + 首次开启确认）。
- 三件事在开放第三方生态前必须补齐：签名校验实现（`WinVerifyTrust` 或等效）、审核清单的格式与更新通道、清单不可得（离线/超时）时的降级策略。
- 启动报告需区分四种准入结果：内置 / 已审核 / 开发者模式 / 拒绝（附原因），并与已装载、被隔离并列输出。
- 管理面必须常显当前准入模式；用户可见文案必须写清"插件与 StarPie 同权限"，不得暗示插件被沙箱隔离。
- 宿主状态需记录准入来源（内置 / 审核清单 / 开发者模式）与签名主体，供诊断与撤销使用。
- 若进程外后端在复启判据成立后立项（决策 6），本 ADR 的"进程内全信任"条款限定在进程内后端，不自动扩展到新后端。
- 清单不可得的降级策略取**保守拒绝**（降级为空清单，不沿用上次缓存）；签名校验按包入口程序集，证书级 CRL 吊销检查关闭而"撤销通道"指向清单的版本级黑名单——两条现行落点见 `docs/architecture/plugin-contracts.md` §5。
